# OpenMausBot project instructions

OpenMausBot is a Node 24+, pnpm-managed React 19/Vite 7 application with a plain Node harness server and Electron desktop shell.

## Development commands

- Install dependencies: `pnpm install`
- Web UI: `pnpm dev`
- Harness server: `pnpm dev:server`
- Desktop app: `pnpm dev:desktop`
- Type-check: `pnpm typecheck`
- Tests: `pnpm test`
- Production build: `pnpm build`
- Trello sync: `pnpm trello:sync`

Before changing code, inspect the relevant implementation and the repository documentation. Keep the server portable across macOS, Windows, and Linux. Put platform-specific behavior in `electron/` behind a `process.platform` guard. Do not hand-edit `dist-server/`; it is generated by `pnpm build:server`.

Server changes require tests. Use the fakes in `server/testing/`, wait for observable events instead of sleeps, and never let tests touch the real `~/.openmausbot`. Preserve the write-only treatment of API keys. Never construct shell command strings or enable `shell: true`; pass untrusted values through argv.

## Automated version control

Whenever you modify source code, documentation, or configuration, create a local Git commit with a descriptive, professional message. Do not push without an explicit user request.

Preserve unrelated user changes in a dirty worktree. Stage and commit only files belonging to the current task. Do not commit generated output or lockfile churn unless it is required by the task.

## Project board

The repository-native project board lives in `docs/dev/fixes/`. Read `docs/dev/fixes/README.md` before creating, reading, or modifying a board file.

- Filename status: `todo--<scope>.md`, `doing--<scope>.md`, `review--<scope>.md`, `done--<scope>.md`.
- Line-item status: `- [ ]` todo, `- [~]` doing, `- [?]` review, `- [x]` done.
- Auditors create `todo--` documents and do not modify application code.
- Implementers pick up `todo--` or `doing--` documents, implement the work, change completed items to `[?]`, and move the document to `review--`.
- Implementers never self-approve. Only the user or a designated reviewer changes `[?]` to `[x]` and moves the document to `done--`.
- Route new audit and implementation work through this board.

For complex implementations, write a technical plan under `docs/dev/plans/` and obtain explicit user approval before changing application code.

## Trello synchronization

Trello mirroring is optional until credentials are configured as described in `docs/dev/fixes/TRELLO.md`. Once enabled, run `pnpm trello:sync` whenever you create a status-prefixed board document, rename one to change its status, or update a line-item checkbox.

If synchronization fails, keep the local Markdown change and report that remote synchronization is pending. Never claim the board is synchronized unless the command succeeds.
